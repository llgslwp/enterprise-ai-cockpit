# Design

## Context

系统已有 `knowledge-base` 能力（检索问答：解析/分块/检索/生成），但缺乏「文件从哪来、如何管理」这一环。本次新增 `knowledge-management` 能力，定位为知识库的**文件管理端**，是 knowledge-base 的上游。二者通过「入库类型」与「文件」关联：本模块负责文件入库与版本管理，后续 knowledge-base 的 RAG 索引直接消费 `data/knowledge/` 下的文件。

## Goals / Non-Goals

**Goals:**
- 新增「知识管理」模块，单页承载文件上传 + 列表管理。
- 文件类型限定 MD/TXT/docx/PDF，拖入或点击上传。
- 入库类型三分类（工艺类/制度类/知识类）标注。
- 版本管理：保留历史版本文件，可查看/下载/回滚。
- 文件启停 + 可见范围标签。

**Non-Goals:**
- 不做文件物理删除（停用即「下线」，文件保留）。
- 不做真实权限拦截（可见范围仅标签）。
- 不做内容解析 / OCR / RAG 索引（本模块只存文件，检索问答由 knowledge-base 后续单独接；扫描版 PDF OCR 已规划在二期）。
- 不做多用户、多端、云存储。

## Decisions

- **存储结构**（本地 `data/knowledge/`，按入库类型分文件夹）：
  ```
  data/knowledge/
  ├── meta.json              # 元数据索引（所有文件当前状态）
  ├── 工艺类/<file_id>/      # 每个文档一个目录，按入库类型归类
  │   ├── v1_<原文件名>
  │   └── v2_<原文件名>
  ├── 制度类/<file_id>/...
  └── 知识类/<file_id>/...
  ```
  - `file_id` 用时间戳 + 随机串生成，避免文件名冲突。
  - 版本文件以 `v{n}_<原文件名>` 命名，保留全部历史版本实体。
  - 目录层级 = 入库类型 → 文件 ID，磁盘上肉眼即可按工艺/制度/知识三类归类翻看。

- **元数据字段**（meta.json 每条）：
  `id`、`name`（原文件名）、`type`（工艺类/制度类/知识类）、`visibility`（可见范围标签）、`status`（enabled/disabled）、`current_version`（当前版本号）、`versions`（[{version, file_path, size, uploaded_at, remark}]）、`created_at`、`updated_at`。

- **可见范围标签取值**：默认枚举 `全员 / 生产 / 质量 / 管理`，默认「全员」，仅作元数据记录、不拦截。取值可后续按业务调整。

- **入库类型**：固定三分类 `工艺类 / 制度类 / 知识类`（用户明确），上传时三选一。

- **版本与回滚语义**：
  - 上传新版本 → 存 `v{n+1}_<原文件名>`，`current_version` 更新为 n+1，旧版本文件保留。
  - 回滚 = 将某历史版本**复制为新版本** `v{n+1}`（版本链单调递增，不重写历史），`current_version` 指向新版本。

- **启停语义**：`status` 字段翻转；停用后文件仍保留在磁盘与列表（列表默认全部展示，停用项置灰标记），后续 RAG 索引时跳过停用文件。

- **并发与一致性**：后端单进程（`reload=False`），元数据读写无并发竞争，直接读写 `meta.json` 即可；每次变更后原子写回。

- **文件类型校验**：按扩展名白名单（`.md/.txt/.docx/.pdf`），大小写不敏感；非法类型拒绝并提示。

## Risks / Trade-offs

- [可见范围标签取值未最终确认] → 采用默认枚举（全员/生产/质量/管理），标注可调整；正式启用前由业务方确认取值范围。
- [回滚复制产生冗余副本] → 换取「版本链不可变、可追溯」的简单性；文件量不大，磁盘开销可接受。
- [meta.json 单文件] → 单机单账号够用；若未来文件量巨大或多端，再迁数据库（本期不引入）。
