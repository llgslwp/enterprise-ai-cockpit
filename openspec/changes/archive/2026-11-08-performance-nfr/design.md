# Design

## Context

系统此前无性能约束的 spec，导致供应链页面 15-20s、质量工具加载失败等性能问题被「功能跑通」掩盖。本次把性能分层约束补进 `system-platform` 行为契约，并配套一条流程规则，让今后新增功能被强制声明性能约束。

## Goals / Non-Goals

**Goals:**
- 在行为契约层固化响应时间分层约束（交互反馈/常规查询 ≤200ms；批量计算/文件生成/LLM 问答豁免 + 进度反馈）。
- 让 OpenSpec 验收能对照性能 requirement，不再靠 AI 自觉。

**Non-Goals:**
- 本变更不优化生产管理页面（约 2s 未达标）——那是后续独立变更。
- 本变更不引入监控/埋点基础设施，仅立约束与验收判据。

## Decisions

**决策 1：性能约束归属 `system-platform`，不新建独立 capability**
- 理由：`system-platform` 定位是「整体运行约束」，已承载「后端单进程」「启动就绪」等运行质量约束，响应时间约束与之同类；集中在一个全局能力里，避免全局约束散落多处。
- 备选：新建 `non-functional-requirements` capability——被否，会与 system-platform 的「整体运行约束」职责重叠。

**决策 2：分层而非一刀切 200ms**
- 理由：批量计算/文件生成（数秒~数十秒）与 LLM 问答（2~20s）本质不可能 200ms，一刀切会令约束形同虚设或这俩功能永远「不达标」。分层后 200ms 只约束交互反馈与常规查询，其余用「进度反馈 + 完成提示」约束。
- 备选：所有操作一律 200ms——被否，违背操作本质。

**决策 3：200ms 定义在「端到端」口径**
- 理由：本地部署 127.0.0.1，网络耗时≈0，端到端≈后端计算 + 前端渲染，统一口径可验收。
- 备选：只约束后端接口耗时——被否，会漏掉前端渲染延迟。

## Risks / Trade-offs

- [生产模块当前约 2s，立标后短期内「不达标」] → 缓解：明确本变更只立约束，达标优化是后续独立变更，不混入本变更。
- [批量计算「完成时间上限」未定死] → 缓解：约束里写「按具体功能另行约定」，不虚构数字，留待各功能 propose 时明确。

## Open Questions

- 批量计算/文件生成的完成时间上限，待各具体功能 propose 时另行约定（本变更不虚构统一秒数）。
