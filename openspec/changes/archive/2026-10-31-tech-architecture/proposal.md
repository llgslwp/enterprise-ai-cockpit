# Proposal

## Why

系统底座（system-foundation）与库存数据建模（inventory-data-model）已就位，但业务功能开发之前，有若干直接影响代码形态的架构决策尚未正式确立。

**项目根本目标（重点声明）**：本项目的首要目的，是打造一个**制造业场景下的 Agent 典型案例**，作为个人开发能力证明，上传 GitHub 用于应聘 FDE（Field/Forward Deployed Engineer）、AI 落地应用工程师、产品经理等 AI 岗位。因此系统设计围绕「多用户参与 + 云端大模型（Agent）+ 企业知识库（RAG）」展开，核心能力需达到可对外展示的工程水准。

经过需求澄清，系统的真实定位比此前理解的更完整：这是一个**多角色协作的驾驶舱**，而非单账号查看数据的工具。此前被简化的两项需求，实为整套设计的基石：

1. **多用户登录**（需求原文「多用户登录低并发使用」）实为**多角色体系**：保管员（上传 ERP 导出的库存文件，替代微信传文件）、生产副总（查看文件上传状态、文件齐后以自然语言触发「写回」等操作）、总经理（查看数据汇总看板）、质检员（质量数据）。此前落地的「单管理员」是错误定位。
2. **企业知识库**（生产工艺、作业指导书）是整体设计的一部分，很可能作为自然语言操作的检索源，非「本期范围外可忽略项」。

此外，「自然语言触发操作」（如「文件齐了，开始写回」）是核心能力而非远期愿景，须纳入架构。

本提案确立技术架构基线：前端选型、接口契约、鉴权、存储，并**按多角色底座设计、本期以单账号过渡**，本期跑通「上传 → 写回/排产 → 汇总」最小闭环。

## What Changes

确立技术架构决策基线，将系统从「纯服务端渲染 + 单管理员」升级为「前后端分离 + 多角色底座（本期单账号过渡）」。

- **前端**：Vue 3 + Vite 单页应用（SPA），与 FastAPI 后端前后端分离。图表 / 看板用前端图表库（如 ECharts）消费 JSON。
- **接口契约**：后端统一提供 REST API + JSON，以 FastAPI 自带 OpenAPI（Swagger UI）作为唯一接口契约载体，接口统一 `/api/` 前缀。
- **鉴权**：Session + Cookie（延续现状），前端 fetch 携带凭证；跨域通过 CORS 允许凭证解决。
- **登录（架构定位）**：按**多角色体系**设计（保管员 / 生产副总 / 总经理 / 质检员），本期以**单账号过渡**实现，多角色后续逐个启用。
- **文件上传**：保管员端口上传 ERP 导出的库存文件（替代微信传文件），是数据进入系统的正式入口能力。
- **自然语言操作**：生产副总以自然语言触发「写回」等操作，是核心能力，纳入架构，本期验证可行性。
- **云端大模型（Agent）**：自然语言操作调用**国内云端大模型**（不本地部署），是案例的核心展示点，本期纳入，通过抽象接入层对接。
- **知识库（RAG）**：生产工艺 / 作业指导书，纳入总体架构，作为 RAG 检索能力载体。本期**预留架构、不建设内容**，后续用 `docs/产品工艺/` 已沉淀知识作为初始知识库。
- **存储**：无数据库、纯文件。业务数据源为 `data/raw/` 下上传的 Excel；非 Excel 数据（账号、配置）走配置文件 / 环境变量；计算结果落 `data/output/` 下的 Excel 文件。

## Capabilities

### Modified Capabilities
- `system-platform`: 系统底座从「Jinja2 服务端渲染 + 单管理员」扩展为「前后端分离 SPA + 多角色底座（本期单账号过渡）」，新增接口契约、文件上传、自然语言操作、汇总看板的架构承载。

### New Capabilities
- `api-contract`: REST API 统一契约约定（路径风格、请求 / 响应结构、错误码、鉴权、文件下载方式），以 FastAPI OpenAPI 为唯一契约载体。
- `agent-core`: Agent 核心能力（云端大模型接入层 + 自然语言意图识别），作为案例核心展示点。

## Impact

- **新增代码**：前端工程（Vue 3 + Vite，`web/`）、CORS 中间件、REST 接口骨架、文件上传接口、Agent 接入层（云端大模型）。
- **修改代码**：`main.py`（挂 CORS、调整路由）、`app/auth.py`（登录适配 SPA + 预留多角色模型）。
- **依赖既有能力**：`admin-auth`（登录态）、`data-access`（纯文件边界）、`inventory-data-model`（读取层）。
- **不引入**：数据库、ORM、JWT 鉴权框架、Node 服务端（Vite 仅作构建 / 开发服务器）、本地大模型部署。
- **分期实现**：多角色、知识库（RAG）为架构正式能力，本期最小闭环为「单账号 → 上传 → 写回/排产 → 汇总」，云端大模型 Agent 本期验证，其余分期启用。
- **展示优先级**：核心能力（多角色 + 云端大模型 + RAG）做到可上 GitHub 的展示级（README / 架构图 / 注释 / 演示路径），边缘功能保持实用。
- **需求差异澄清**：需求原文「多用户登录」与「企业知识库」**均在本项目总体设计范围内**，非被排除；此前「排除知识库」「单管理员」的记录是对需求的理解偏差，已在本提案纠正。
