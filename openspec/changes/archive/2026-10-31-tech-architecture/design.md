# Design

## Context

底座（system-foundation）已落地 FastAPI + Jinja2 服务端渲染 + Session 登录；库存数据建模（inventory-data-model）已落地纯文件读取层。业务功能（上传 / 写回 / 排产 / 汇总）开发前，需先确立技术架构基线。

**项目根本目标**：打造「制造业 × Agent」典型案例，作为个人能力证明（GitHub，应聘 FDE / AI 落地应用工程师 / 产品经理）。因此核心能力需达到可对外展示的工程水准。

经需求澄清，系统真实定位为**多角色协作驾驶舱**（保管员 / 生产副总 / 总经理 / 质检员），此前「单管理员」是理解偏差。本变更确立架构基线，按多角色底座设计、本期单账号过渡。

## Goals / Non-Goals

**Goals:**
- 确立技术决策：前端选型（Vue 3 + Vite）、接口契约（REST + OpenAPI）、鉴权（Session + Cookie）、存储（无数据库纯文件）、云端大模型接入（国内云端，不本地部署）。
- 按**多角色底座**设计：角色 / 权限 / 文件上传 / 自然语言操作 / 汇总看板 / 知识库均为正式能力。
- 本期以单账号过渡，跑通「上传 → 写回/排产 → 汇总」最小闭环，并验证云端大模型 Agent 的自然语言操作。
- 核心能力（多角色 + 云端大模型 + RAG）达到展示级工程水准。
- 纠正此前对「多用户登录」「企业知识库」的理解偏差，如实记录。

**Non-Goals:**
- 不引入数据库 / ORM / JWT / Node 服务端 / 本地大模型部署。
- 本期不实现多角色逐个启用、知识库（RAG）内容建设（属分期）。
- 不改需求说明书原文，仅在工件中记录澄清结论。

## Decisions

### 决策 1：前端 = Vue 3 + Vite SPA
现状 Jinja2 服务端渲染无法高效支撑「汇总看板生成图表」。选定 Vue 3 + Vite 前后端分离，图表用 ECharts 消费 JSON。前端工程独立目录（`web/`），开发期 Vite dev server 与 FastAPI 分端口运行，生产期构建产物由 FastAPI 静态托管。

### 决策 2：接口契约 = REST API + JSON，以 FastAPI OpenAPI 为唯一契约
- 后端统一提供 REST 接口，请求 / 响应均为 JSON（文件下载除外）。
- FastAPI 自动生成的 OpenAPI（Swagger UI）作为接口契约的唯一载体，不另写 Markdown 接口文档。
- 接口路径统一挂 `/api/` 前缀，避免与前端静态资源冲突。

### 决策 3：鉴权 = Session + Cookie，CORS 允许凭证
- 延续现状 Session + Cookie。
- 前端 fetch 用 `credentials: "include"` 携带 Cookie。
- 后端 CORS 配置允许前端开发端口并开启 `allow_credentials=True`，生产期同源则无需 CORS。

### 决策 4：登录 = 多角色底座，本期单账号过渡
- 架构上按多角色体系设计：保管员 / 生产副总 / 总经理 / 质检员，各自有对应端口与权限。
- 本期先以单账号过渡实现，多角色后续逐个启用（分期）。
- 数据模型层面为角色 / 权限预留扩展点，避免未来重构。

### 决策 5：文件上传 = 数据进入系统的正式入口
- 保管员端口上传 ERP 导出的库存文件，替代此前「微信传文件」的做法。
- 上传文件落入 `data/raw/`（沿用既有数据入口约定），作为后续计算的输入源。

### 决策 6：自然语言操作 = 核心能力，接云端大模型，本期验证
- 生产副总以自然语言触发「写回」等操作（如「文件齐了，开始写回」）。
- 是核心能力，纳入架构。本期以最小可行方式验证（自然语言 → 意图识别 → 触发既有写回/排产链路），不做完整 Agent 体系。
- **调用云端大模型（国内），不本地部署**。通过抽象 LLM 接入层对接，具体厂商在 apply 阶段确定，避免与厂商强绑定。

### 决策 7：知识库（RAG）= 纳入总体架构，本期预留不建内容
- 生产工艺 / 作业指导书纳入总体架构，作为 RAG 检索能力载体，可能作为自然语言操作的检索源。
- 本期**预留架构、不建设内容**；后续用 `docs/产品工艺/` 已沉淀知识作为初始知识库。
- 是案例的三大核心展示点之一（多角色 + 云端大模型 + RAG），架构上须预留清晰的扩展位。

### 决策 8：存储 = 无数据库、纯文件
- 业务数据源：`data/raw/` 下上传的 Excel（已处理）。
- 非 Excel 数据（账号、配置）：配置文件 / 环境变量。
- 计算结果：落 `data/output/` 下的 Excel 文件。
- 不引入 SQLite / 任何数据库。

### 决策 9：展示优先级 = 兼顾，核心能力展示级
- 核心能力（多角色 + 云端大模型 + RAG）做到可上 GitHub 的展示级：README 项目介绍、架构图、代码注释、演示路径清晰可复现。
- 边缘功能保持实用即可，不为展示投入过度。

### 决策 10：人机交互 = 对话为主、全局智能助手、先蓝图后闭环
- **交互主形态**：对话为主、按钮为辅。核心操作以自然语言对话驱动，按钮/表单兜底。
- **入口形态**：全局智能助手（常驻，理解当前角色与数据状态，权限随角色收敛）。
- **流程**：意图识别 → 参数补齐 → 确认（仅副作用操作）→ 执行 → 反馈五步闭环。
- **副作用操作确认**：写回/排产等有副作用操作执行前确认；查询类直接返回。
- **设计路径**：先产出完整交互蓝图（`docs/交互设计/人机交互蓝图.md`），再从蓝图中抠出本期核心闭环（登录→上传→写回/排产→汇总 + 全局助手最小可用）实现。

### 决策 11：意图识别 = 规则为主、大模型兜底
- 先用关键词/规则快速匹配常见指令（写回/排产/上传/查询），匹配不上再交给云端大模型兜底分类。
- 理由：工厂操作指令种类有限，规则可覆盖大多数，大模型兜底口语表达，兼顾稳定与省调用。
- 权限收敛两层：身份层（会话携带角色）+ 能力层（角色→允许操作清单），越权时友好提示而非静默拒绝。

### 决策 12：对话编排 = 自研轻量编排引擎（不用现成 Agent 框架）
- 自研实现意图识别、参数补齐、状态机、副作用确认、结果反馈五步闭环，大模型仅做兜底分类。
- 不用 LangChain / 飞书 aily / Dify 等现成 Agent 框架。
- 理由：本项目是「能力证明」案例，自研编排的意图识别、状态机、确认机制是「懂 Agent 原理」的核心展示资产；工厂场景意图种类少、对话浅，无需框架重能力。

### 决策 13：云端大模型 = 抽象接入层 + OpenAI 兼容，首选 DeepSeek
- 定义统一 LLM 接入接口（抽象层），首个实现用 OpenAI 兼容格式（换 base_url + key 即可切换厂商）。
- 首个厂商选 DeepSeek（性价比高、OpenAI 兼容、国内可直连）；后续可切换通义千问 / 智谱 GLM 等。
- 不本地部署大模型。

## Risks / Trade-offs

- [SPA 增加构建链] 前后端分离需维护 Vue 工程与 Node 构建链 → 选定 SPA 的固有代价，通过「前端仅消费 OpenAPI 契约」降低沟通成本。
- [多角色 vs 单账号过渡] 架构多角色但本期单账号，存在「架构设计超前、实现滞后」的张力 → 通过「数据模型预留角色扩展点、本期仅启用单账号」缓解，避免未来重构。
- [自然语言操作风险] 意图识别准确性不稳定 → 本期仅验证「自然语言 → 触发既有链路」的可行性，不做完整 Agent，风险可控。
- [跨域复杂度] 开发期前后端分端口 → 在 `api-contract` 规格中显式规定 CORS 允许来源与凭证。
