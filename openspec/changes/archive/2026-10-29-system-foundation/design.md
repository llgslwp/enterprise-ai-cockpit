# Design

## Context

本项目是宏润管钳厂的企业 AI 驾驶舱，Web 应用形态。当前无既有代码，属于全新（greenfield）项目。本变更只做系统底座：Web 运行框架、单管理员登录、数据接入约定。生产/库存/质量三个业务模块由后续变更承接，企业知识库与多用户登录不在范围内。数据前提：数据进入本项目前已经过处理，本项目不做 ERP 对接、不做数据清洗（详见 `项目需求说明书.md`）。

## Goals / Non-Goals

**Goals:**
- 确立 Web 应用底座与三个业务模块的分层边界。
- 确立单管理员登录作为业务模块的统一访问前置。
- 固化数据接入约定，防止后续模块误引入 ERP 对接或数据清洗。

**Non-Goals:**
- 不实现生产管理、库存管理、质量管理的任何业务逻辑。
- 不实现企业知识库、多用户/多角色登录。
- 不选定具体前端框架或数据库产品（属实施细节，apply 阶段按需决定）。

## Decisions

**决策 1：底座与业务模块分层**
- 理由：登录与运行框架是三个业务模块共同依赖的横切能力，先立底座可避免三个模块各自实现一遍登录。
- 备选：登录内嵌到首个业务模块——被否，会导致后续模块复用困难、登录逻辑重复。

**决策 2：单管理员账号（不做多用户）**
- 理由：需求明确本次范围不含多用户登录，且生产/库存/质量数据仅限内部管理员访问，单账号即可满足。
- 备选：直接做多用户多角色——被否，超出本次范围，增加不必要的复杂度。

**决策 3：数据接入约定固化为契约，而非实现**
- 理由：需求边界「不做 ERP 对接、不做清洗」是硬约束，必须在规格层固化，防止实施阶段误越界。
- 备选：仅在文档提及、不纳入规格——被否，边界不硬化会在后续模块实施时被突破。

## Risks / Trade-offs

- [单账号登录安全性弱] → 缓解：本变更明确为「最简登录」，后续如需要可独立变更升级为多用户；Web 应用部署时配合密码强度与访问控制。
- [数据来源形式未定（文件 vs 已处理数据库）] → 缓解：本变更只固守「已处理」契约，不绑定具体形式；具体载体在首个业务模块提案时确定，属可后置的 Open Question。
- [底座过度设计风险] → 缓解：本变更仅定边界与契约，不落地实现细节，避免过早引入框架绑定。

## Open Questions

- 已处理数据进入本项目的具体载体（Excel 文件 / CSV / 数据库）——由后续生产管理模块提案时确定，不影响本变更的规格与任务拆解。
