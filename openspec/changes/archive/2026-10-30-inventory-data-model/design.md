# Design

## Context

本变更建立库存数据模型与读取层。数据源为两类已导出文件：ERP 导出的五类库存 Excel（毛坯库、半成品库、外协、车间在产品、在产品装配）与腾讯文档成品入出库新台账，各自一个 Excel 文件。约束：按原始字段原样承接，不重命名、不合并、不归一化（见 proposal 与 data-access 规格）。生产管理、库存管理将基于本能力展开。

## Goals / Non-Goals

**Goals:**
- 定义五类库存数据 + 成品台账的统一数据结构。
- 实现 Excel 读取层，将各类文件读入统一结构，字段原样承接。
- 建立字段字典，保证字段可溯源。

**Non-Goals:**
- 不实现生产计划计算、库存状态展示等任何业务逻辑。
- 不修改、不校验字段的业务含义（数据已处理，本项目只消费）。
- 不选定具体数据库产品（当前以内存/DataFrame 结构承载即可）。

## Decisions

**决策 1：以「统一结构」而非「强 Schema」承载五类数据**
- 理由：五类数据的字段各不相同，若强行统一成一张表会破坏「原样承接」约束；以统一的结构约定（每类数据独立的数据结构 + 元信息）承载，既统一又不损字段原样。
- 备选：强行合并成单一大宽表——被否，会迫使字段重命名/合并，违反原样承接。

**决策 2：字段原样承接，仅做「类型无关的字符串/原始值」读取**
- 理由：ERP 导出字段可能包含编码、空值、格式差异，本项目不做清洗，读取时保留原始值，避免在读取层引入隐含的语义改造。
- 备选：读取时做类型转换/去空格——被否，属于清洗，越界。

**决策 3：字段字典用「声明式描述」而非「代码内硬编码」**
- 理由：字段来源与含义需要可溯源、可维护，声明式字典比散落在代码里的常量更清晰，也便于后续模块引用。
- 备选：字段名直接硬编码在读取函数里——被否，字段字典缺失，溯源困难。

## Risks / Trade-offs

- [五类文件的实际字段名/结构未知] → 缓解：本变更按「原样承接」设计为字段无关的读取框架，具体字段在拿到样例文件后录入字段字典，读取层不因字段差异而改动。
- [Excel 格式差异（表头行、合并单元格）] → 缓解：读取层预留表头定位与数据区识别，遇到差异时记录为待确认，不猜测。
- [过度设计风险] → 缓解：只做读取与结构化，不引入数据库、不引入 ORM，保持轻量。

## Open Questions

- 五类库存文件与成品台账的具体文件名、字段名、表头结构——待拿到样例文件后录入字段字典，不影响本变更的规格与任务拆解（读取层为字段无关设计）。
