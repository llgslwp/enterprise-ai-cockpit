# system-platform Specification

## Purpose

定义驾驶舱作为 Web 应用的整体运行约束与模块承载边界，明确本次范围内各功能模块的归属关系，以及底座与业务模块的分层职责。

## Requirements

### Requirement: Web 应用形态
驾驶舱系统 SHALL 以 Web 应用形态运行，用户通过浏览器访问。

#### Scenario: 浏览器访问
- **WHEN** 用户访问驾驶舱
- **THEN** 系统 MUST 以 Web 页面形式提供服务，无需安装客户端程序

### Requirement: 模块承载边界
系统 SHALL 明确本次范围内各功能模块的归属：生产管理、供应链管理（原库存管理）、质量管理、知识管理为四个业务模块，登录为统一访问前置，多用户登录不在本次范围内。

#### Scenario: 模块归属判定
- **WHEN** 需要判定某一功能是否属于本次系统底座承载范围
- **THEN** 生产管理、供应链管理、质量管理、知识管理 MUST 判定为在范围内，多用户登录 MUST 判定为不在范围内

### Requirement: 底座与业务模块分层
系统底座 SHALL 与业务模块分层，底座负责运行框架与登录，业务模块（生产/库存/质量）基于底座承载。

#### Scenario: 业务模块依赖底座
- **WHEN** 后续落地生产、库存、质量任一业务模块
- **THEN** 该模块 MUST 基于本系统底座承载，复用底座提供的运行框架与登录入口

### Requirement: 前后端分离架构
系统 SHALL 采用前后端分离架构：前端为 Vue 3 + Vite 单页应用，后端为 FastAPI 提供 REST 接口。

#### Scenario: 前端与后端分离
- **WHEN** 用户使用驾驶舱前端页面
- **THEN** 前端 MUST 为独立构建的 Vue 3 应用，通过 REST 接口向后端获取数据，而非服务端渲染页面

### Requirement: 多角色底座
系统 SHALL 按多角色体系设计：保管员、生产副总、总经理、质检员各自拥有对应端口与权限。

#### Scenario: 角色端口职责
- **WHEN** 需要判定某一角色的职责归属
- **THEN** 保管员端口 MUST 承载上传 ERP 导出库存文件，生产副总端口 MUST 承载查看文件上传状态与触发操作，总经理端口 MUST 承载查看数据汇总看板，质检员端口 MUST 承载查看质量管理数据的分析

### Requirement: 本期单账号过渡
系统本期 SHALL 以单账号过渡实现登录，多角色体系后续分期启用。

#### Scenario: 单账号过渡
- **WHEN** 本期用户登录系统
- **THEN** 系统 MUST 以单账号提供访问，同时数据模型 SHALL 为多角色 / 权限预留扩展点，避免未来重构

### Requirement: 文件上传入口
系统 SHALL 提供文件上传能力，作为 ERP 导出数据进入系统的正式入口，替代微信传文件的做法。

#### Scenario: 保管员上传库存文件
- **WHEN** 保管员上传 ERP 导出的库存文件
- **THEN** 系统 MUST 接收文件并落入数据入口目录（`data/raw/`），作为后续计算的输入源

### Requirement: 自然语言操作
系统 SHALL 支持以自然语言触发操作（如「文件齐了，开始写回」），作为生产副总端口的核心交互方式。

#### Scenario: 自然语言触发写回
- **WHEN** 生产副总以自然语言发出操作指令
- **THEN** 系统 MUST 识别意图并触发对应的既有计算链路（写回 / 排产）

### Requirement: 知识库纳入架构
系统 SHALL 将企业知识库（生产工艺、作业指导书、公司制度、行业知识）纳入总体架构，作为 RAG 检索能力载体，分期实现；本期落地知识管理（文件上传与管理），RAG 检索问答后续分期。

#### Scenario: 知识库架构承载
- **WHEN** 评估知识库在系统中的地位
- **THEN** 知识库 MUST 视为总体架构的一部分，本期落地文件管理（知识管理模块），RAG 检索问答与索引后续分期建设

### Requirement: 后端运行进程形态
系统 SHALL 以后端单进程形态运行，MUST NOT 启用 uvicorn 的 `reload=True` 热重载，以避免「主进程 + reloader 子进程」双进程结构导致的端口争抢、孤儿进程与后端掉线。

#### Scenario: 后端单进程常驻
- **WHEN** 系统启动后端服务
- **THEN** 后端 MUST 以单进程运行（仅一个 python 进程），MUST NOT 存在 reloader 子进程

#### Scenario: 代码变更后重启生效
- **WHEN** 后端代码发生变更
- **THEN** 系统 SHALL 通过手动重启后端加载新代码，而非依赖 reload 热重载

### Requirement: 启动就绪等待
系统 SHALL 在启动脚本中等待后端服务真正就绪后再打开浏览器，以避免浏览器早于后端就绪导致用户登录时连接被拒、误报「登录失败」。

#### Scenario: 后端就绪后才打开浏览器
- **WHEN** 用户运行一键启动脚本启动驾驶舱
- **THEN** 启动脚本 MUST 轮询等待后端 8000 端口进入 LISTEN 状态后，才打开浏览器指向前端地址

#### Scenario: 后端未就绪时明确提示
- **WHEN** 启动脚本在等待超时（60 秒）后后端仍未就绪
- **THEN** 启动脚本 MUST 明确提示「后端未就绪」，而非让用户在不知情下直接登录

### Requirement: 响应时间性能约束
系统 SHALL 遵守分层响应时间约束：交互反馈与常规查询 MUST 在 200ms 内响应，批量计算、文件生成与知识库问答 MUST 提供即时进度反馈，交付前 MUST 做性能回归。

#### Scenario: 交互反馈延迟
- **WHEN** 用户在前端执行任一操作（点击、切换、提交）
- **THEN** 系统 MUST 在 200ms 内出现可感知反馈（如加载态、状态变化），不得出现无反馈的卡顿

#### Scenario: 常规查询与列表加载
- **WHEN** 用户请求常规查询或列表加载（后端读文件 + 前端渲染）
- **THEN** 系统 MUST 在 200ms 内完成端到端响应

#### Scenario: 批量计算与文件生成
- **WHEN** 用户触发批量计算或文件生成导出（如全量重跑排产、导出 Excel）
- **THEN** 系统 MUST 立即给出进度反馈并在完成时明确提示，该场景不适用 200ms 硬约束，完成时间上限按具体功能另行约定

#### Scenario: 知识库问答
- **WHEN** 用户发起知识库问答（RAG + LLM 生成）
- **THEN** 系统 MUST 采用流式输出或进度反馈，不适用 200ms 硬约束

#### Scenario: 交付前性能回归
- **WHEN** 任一功能准备交付
- **THEN** 开发方 MUST 用真实数据量执行性能回归并记录响应时间基线，超约束视为未完成
