# agent-core Specification

## Purpose
定义 Agent 核心能力：云端大模型接入层与自然语言意图识别。这是本项目作为「制造业 × Agent」典型案例的核心展示点，自然语言操作通过调用国内云端大模型实现，不本地部署。

## Requirements

### Requirement: 云端大模型接入
系统 SHALL 通过统一接入层调用云端大模型（国内厂商）实现自然语言问答与知识库生成能力，不本地部署大模型。

#### Scenario: 调用云端大模型
- **WHEN** 系统需要理解自然语言问题或生成回答
- **THEN** 系统 MUST 通过云端大模型 API 完成，而非本地部署模型

#### Scenario: 厂商可切换
- **WHEN** 需要更换云端大模型厂商
- **THEN** 系统 SHALL 通过抽象接入层隔离厂商差异，更换厂商不改动业务逻辑

### Requirement: 对话主交互形态
系统 SHALL 以「对话」作为智能辅助决策的主交互形态，用户以自然语言提问，系统返回基于工具调用（含知识库检索）生成的回答。对话接口 SHALL 接受最近 N 轮历史，支持多轮上下文。

#### Scenario: 核心操作经对话驱动
- **WHEN** 用户以自然语言提出业务数据或知识问题
- **THEN** 系统 SHALL 通过对话返回基于工具调用或知识库检索生成的回答

#### Scenario: 多轮上下文
- **WHEN** 用户的追问依赖上文（含指代或省略主语）
- **THEN** 系统 SHALL 结合历史将追问改写为完整独立查询后再回答，不得按单轮孤立理解而答非所问

### Requirement: 缺口查询工具
系统 SHALL 提供只读工具 `query_gap`，查询最新排产结果的缺口数据（装配缺口、机加工缺口）与成品计划、半成品需求计划，供 agent 回答「还差多少」类排产决策问题。

#### Scenario: 按规格查缺口
- **WHEN** 用户询问某规格的缺口（如「71-75 还差多少」）
- **THEN** 模型 MUST 调用 `query_gap`，返回该规格的成品计划与各配件缺口；「装配缺口」「机加工缺口」两列以方向标注结构返回（`{"缺口": n, "富余": 0}` / `{"缺口": 0, "富余": n}`，null=无此工序），模型 MUST 照读方向、不得凭绝对值大小判方向；「半成品需求计划」返回裸数字（需求计划量，恒 ≥ 0），MUST NOT 当作缺口解读

#### Scenario: 数据可对账
- **WHEN** `query_gap` 返回缺口数据
- **THEN** 该数据 MUST 与 `gap_stat.extract_gap_stat` 逐值一致，可拿 V2.0 排产结果对账

#### Scenario: 只读无副作用
- **WHEN** agent 调用 `query_gap`
- **THEN** 该工具 MUST 仅查询、不改写排产结果文件

#### Scenario: 性能约束
- **WHEN** agent 调用 `query_gap`
- **THEN** 数据提取耗时 MUST 符合全局 NFR（常规查询 ≤200ms）

### Requirement: 生产完成率查询工具
系统 SHALL 提供只读工具 `query_production`，查询成品生产计划的完成率数据（计划数、完成数、完成率），分 6 品类与 4 区段，供 agent 回答「完成得怎么样」「哪些品类拖后腿」类排产进度问题。

#### Scenario: 按月份查完成率
- **WHEN** 用户询问某月完成率（如「11月完成率多少」「本月完成得怎么样」）
- **THEN** 模型 MUST 调用 `query_production`，返回该月总体 + 6品类 + 4区段的计划数/完成数/完成率

#### Scenario: 按品类查逐月趋势
- **WHEN** 用户询问某品类逐月完成率（如「各月加力钳完成率趋势」）
- **THEN** 模型 MUST 调用 `query_production`（不传 month），从返回的「各月品类完成率」概览中读取该品类各月完成率，不得用「各月完成率」（总体）冒充品类数据

#### Scenario: 完成率语义
- **WHEN** `query_production` 返回完成率
- **THEN** 完成率 MUST 等于 完成数 ÷ 计划数 × 100%；完成率 MAY 超过 100%（表示超产，非错误）；完成率越低表示进度越慢（拖后腿），模型 MUST 照此解读、不得把超 100% 判为异常

#### Scenario: 数据可对账
- **WHEN** `query_production` 返回完成率数据
- **THEN** 该数据 MUST 与 `dashboard_calc` 的计算结果逐值一致，可拿生产计划大屏对账

#### Scenario: 只读无副作用
- **WHEN** agent 调用 `query_production`
- **THEN** 该工具 MUST 仅查询、不改写生产计划文件

#### Scenario: 性能约束
- **WHEN** agent 调用 `query_production`
- **THEN** 数据提取耗时 MUST 符合全局 NFR（常规查询 ≤200ms）

### Requirement: 产能查询工具
系统 SHALL 提供只读工具 `query_capacity`，用确定性代码计算「现有资源可产数量」，返回「可产把数 + 瓶颈件 + 多维度明细」，供 agent 回答「最多能生产多少 / 可产 / 产能」类问题，替代模型自行硬凑。

#### Scenario: 按规格查可产数量
- **WHEN** 用户询问某规格的现有资源可产数量（如「以现有资源最多能生产多少把 71-75」）
- **THEN** 模型 MUST 调用 `query_capacity`，返回该规格的「总可产把数 + 瓶颈件 + 第一/第二维度逐配件明细」；可产把数 = 第一维度可产 + 第二维度追加；瓶颈件由工具返回、模型 MUST 照读，不得自行判断

#### Scenario: 两维口径（钻杆钳）
- **WHEN** `query_capacity` 计算钻杆钳某规格可产数量
- **THEN** 第一维度 MUST 取 min(组装简易钳体·装配I, 活动齿块·半成品H, 自由钳外管·半成品H)；第二维度 MUST 仅在活动齿块和自由钳外管都还有剩余时触发，追加 = min(floor(min(第二维度配件现有量÷用量)), 剩余齿块, 剩余外管)；整除一律向下取整

#### Scenario: 三维口径（加力钳）
- **WHEN** `query_capacity` 计算加力钳公制规格（95D）可产数量
- **THEN** 按「组合件递减」分三维：第一维 = min(三合一组合件·装配I, 大钳口/固定帽/螺母/把手/内管·半成品+装配)；第二维 = min(二合一组合件·装配I, 小钳口/大钳口/固定帽/螺母/把手/内管·半成品+装配 的剩余)；第三维 = min(钳体/小钳口/大钳口/固定帽/螺母/把手/内管·半成品 + 外管·待处理+半成品)；把手全维度额外计入待处理 F；补件维度间顺序消耗；每件用量均为 1

#### Scenario: 阶段 1 规格范围
- **WHEN** 用户询问借件规格（钻杆钳 89-95、114-117）、借用规格（成品计划=0）、加力钳借用规格（108D/152D）或英制规格，或其他品类的可产数量
- **THEN** 工具 MUST 返回明确提示（「借件规格，待阶段 2 支持」/「该规格不单独排产」/「当前产能口径仅支持钻杆钳 54-56、71-75 与加力 95D」），MUST NOT 孤立算成 0 或给出误导数字

#### Scenario: 数据可对账
- **WHEN** `query_capacity` 返回可产数量
- **THEN** 该数据 MUST 与 `capacity._calc_capacity_core`（钻杆钳）/ `capacity._calc_capacity_jiali_core`（加力钳）的确定性计算逐值一致，可拿 V2.0 半成品计划现有量列对账（真值锚点：54-56=210、71-75=627、加力 95D=1176）

#### Scenario: 只读无副作用
- **WHEN** agent 调用 `query_capacity`
- **THEN** 该工具 MUST 仅查询、不改写排产结果文件

#### Scenario: 性能约束
- **WHEN** agent 调用 `query_capacity`
- **THEN** 数据提取与计算耗时 MUST 符合全局 NFR（常规查询 ≤200ms）

### Requirement: 多工具调用
系统 SHALL 支持 agent 通过工具调用循环回答业务数据问题：模型根据用户问题动态决定调用哪些只读工具，执行后观察结果，再决定下一步，直至给出答案。

#### Scenario: 模型选对工具
- **WHEN** 用户提出业务数据问题（如库存、缺口、合格率）
- **THEN** 模型 MUST 判断并调用对应的只读工具查询数据，而非凭记忆编造数字

#### Scenario: 多步编排
- **WHEN** 一个问题需要多个工具串联才能回答（如判断缺料需先查库存再查订单）
- **THEN** 模型 SHALL 根据前一步工具返回的结果，动态决定下一步调用哪个工具

### Requirement: 只读工具边界与写操作拦截
系统 SHALL 仅向 agent 暴露只读查询工具，不暴露任何写操作（写回、排产、回填）。未来若引入写操作工具，MUST 通过人工确认通道，不得由模型直接触发。

#### Scenario: 只读边界
- **WHEN** agent 需要查询业务数据
- **THEN** 它可调用的工具 MUST 仅为只读查询，无副作用、不改写任何数据

#### Scenario: 写操作拦截
- **WHEN** 未来引入写操作工具（如回填、排产）
- **THEN** 系统 MUST 要求人工确认后方可执行，模型不得直接触发

### Requirement: 数据真实性约束
agent 回答中涉及的具体业务数据（数字、数量、比率）MUST 来自工具返回值，模型 SHALL NOT 凭空编造或改动工具返回的数据。

#### Scenario: 数据可对账
- **WHEN** agent 回答包含具体业务数据
- **THEN** 该数据 MUST 与工具返回值逐值一致，可拿台账 / 缺口表对账

### Requirement: 工具调用轨迹可追溯
系统 SHALL 记录每次问答中模型调用的工具及其返回值，支持回放与对账。

#### Scenario: 轨迹记录
- **WHEN** agent 完成一次问答
- **THEN** 系统 SHALL 记录模型调用了哪些工具、各工具返回了什么，供回放对账

### Requirement: 性能约束符合全局 NFR
agent 问答属 LLM 问答豁免类型（不套 200ms 常规查询约束），但 MUST 提供即时进度反馈与完成提示。

#### Scenario: 进度反馈
- **WHEN** 用户发起一次问答
- **THEN** 系统 SHALL 立即返回可感知的进度反馈（如「正在思考」加载态），完成时给出完成提示，不得无反馈卡顿

### Requirement: 多轮上下文与指代消解改写
系统 SHALL 支持多轮对话上下文：当用户追问含指代（「它 / 这个 / 那个 / 其」等）或省略主语、依赖上文时，系统 MUST 先将追问改写成完整独立查询，再进入工具调用，避免模型因单轮失忆答非所问。

#### Scenario: 首轮跳过改写（门控）
- **WHEN** 一次问答的 history 为空（首轮或新话题）
- **THEN** 系统 MUST 跳过改写，原样透传问题进入工具调用，不额外调用大模型

#### Scenario: 有历史才改写
- **WHEN** 一次问答的 history 非空（多轮追问）
- **THEN** 系统 MUST 调用公共改写函数，将含指代的追问改写为完整独立查询，并以改写后的查询进入工具调用

#### Scenario: 改写结果透出
- **WHEN** 系统完成 Query 改写
- **THEN** 系统 MUST 将改写后的查询作为 `rewritten_query` 字段随响应返回，供前端展示「已理解：XXX」；未改写（history 为空）时该字段为空，前端不展示

#### Scenario: 改写失败回退
- **WHEN** 改写返回空或调用失败
- **THEN** 系统 MUST 回退使用原始问题继续问答，不得因改写失败中断

#### Scenario: 历史范围与截断
- **WHEN** 构造改写上下文
- **THEN** 系统 MUST 仅取最近 6 条历史（约 3 轮），单条内容截断至数百字，防止 token 超限

#### Scenario: 公共能力复用
- **WHEN** agent 与知识库两个模块均需改写
- **THEN** 两者 MUST 复用同一公共改写函数，不得各自复制一份，保证口径一致

#### Scenario: 性能约束（LLM 豁免）
- **WHEN** 触发 Query 改写（多一轮 LLM 调用）
- **THEN** 该调用属 LLM 问答豁免类型，不套 200ms 常规查询约束，MUST 提供进度反馈，完成时给出完成提示
