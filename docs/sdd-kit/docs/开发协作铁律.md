# 开发协作铁律（SDD 套件 · 内容方法论层）

> 来源：企业AI驾驶舱项目 2026-10-31 复盘固化。
> 定位：与 OpenSpec 官方流程（流程边界层）叠加执行的「内容方法论」。二者分层、不冲突。
> 效力：以下不是「建议」而是**强制约束**，违反会重犯已踩过的坑。

## 铁律清单

1. **架构基石级需求必问必确认，禁止假设带过**
   凡涉及「多用户/多角色」「知识库/RAG/数据源」「自然语言/Agent 能力」「云端大模型」这类词，一律列为必问项，不得当「次要细节」做假设。
   - 反例教训：把「多用户」「知识库」当次要细节假设 → 架构整体返工。
   - 本条款是 OpenSpec propose 指令「material ambiguity 必问、minor detail 才假设」的**判定标准细化**（不是平行新规则）：把「什么是 material」具体化为上列架构基石关键词。执行时以「这些关键词一律必问」为准。

2. **技术选型必须单独提审**
   前端框架、接口契约、数据库/存储、鉴权方案等架构决策，必须作为独立变更/独立决策点暴露给用户拍板，不得混进功能实现里「隐含」带过。

3. **需求原文是唯一权威基线**
   范围决策若与需求文档冲突，必须同步改原文或在原文处显式标注「范围差异」，不得两处各说各话。

4. **手工 Excel / 台账的列语义与区段结构，动手写代码前先跟用户确认**
   这类输入的语义藏在列名和布局里（如「未完成数量」实为「计划数」），靠猜必错。
   - 反例教训：J/K 列算法猜错被逐条纠正。

5. **规则设计要正向找真判据 + 用反例回归**
   不能「能用就行」，要验证边界情况（会被误伤的样本）。
   - 反例教训：借用行差点用「B列≠块规格」误伤跨规格正常行。

6. **真实数据早接入、每步实跑验证**
   验收标准用「数据驱动的量化对照」（如 37/37、99.1%），不用「看起来对」。

7. **非功能需求（性能/响应时间）纳入需求必问，交付前做性能回归**
   凡涉及「读 Excel / 大数据量 / 批量计算 / 文件生成」的功能，写码前先问「最大数据量、可接受响应时间」；技术选型时评估「这个写法在最大数据量下会不会卡」。
   - 响应时间分层约束（端到端）：交互反馈（点击→可感知反馈）≤200ms；常规查询/列表加载 ≤200ms；批量计算/文件生成/LLM 问答不套 200ms，改「进度反馈 + 完成提示」。
   - 交付前用真实数据量跑一次性能回归，记录响应时间基线，超约束视为未完成。
   - 反例教训：openpyxl 全量加载 177 sheet → 供应链页面 15-20s；并发写固定临时文件 → 质量模块加载失败。
   - 流程硬约束：凡 propose 新增/修改能力，该能力的 spec MUST 声明其性能约束符合全局 NFR（常规查询 ≤200ms），或显式标注豁免类型（批量计算/文件生成/LLM 问答）；未声明不得 apply/archive。

## 与 OpenSpec 的分层关系

| 规则层 | 管什么 | 来源 |
|---|---|---|
| OpenSpec 官方 skill | 流程边界（何时能写码 / 何时归档 / 何时只思考） | 官方 |
| 本铁律 | 内容方法（选型是否提审 / 语义是否确认 / 规则是否反例回归） | 复盘 |

两者一个管「何时停」，一个管「如何对」，叠加执行、互不越界。
