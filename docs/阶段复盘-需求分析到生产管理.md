# 阶段复盘：从需求分析到生产管理模块开发完成

> 复盘范围：企业AI驾驶舱项目从 2026-10-29 需求分析起步，到 2026-10-31 生产管理模块（回填链路 + 半成品排产链路）开发完成的完整流程。
> 目的：提炼「做得好的经验（继续保持）」与「踩坑教训（避免走回头路）」，作为后续新项目的可复用方法论。
> 复盘对象：OpenSpec 规范驱动开发流程本身 + AI 协作方式，而非具体业务逻辑正确性。

## 二、做得好的经验（继续保持）

### 1. 规范驱动开发（OpenSpec）本身是最大的「防回头路」武器
- 每个变更都「先 proposal（为什么改）→ specs（行为契约）→ design（怎么改）→ tasks（拆解）→ apply（落地）→ archive（固化）」。
- **收益**：需求、契约、实现、验收四个层面强制分离，任何一步变更都有据可查；归档后能力永久固化，后续变更可增量叠加而非推倒重来。
- **结论**：这套流程值得在后续所有新项目沿用，尤其适合「需求会反复对齐」的制造业场景。

### 2. 真实数据早接入、早验证（验证性抽查）
- 从 inventory-data-model 起就把真实 ERP 文件放进 `data/raw/`，映射规则、回填、排产每一步都「实跑 + 对照真实文件核对」。
- **收益**：借用了「数据驱动的验收标准」（37/37、99.1%、逐批号一致），避免了「代码写完了但不知道对不对」的空转。
- **结论**：真实数据是最硬的验收标准，比任何假设都可靠。

### 3. 明确「一期/二期」工程分界，控制范围
- 一期只做「跑通链路」，把「代码复刻公式、自动上传腾讯文档、sheet 重构」三项明确划到二期并登记，不做。
- **收益**：避免了一次性铺太开导致无法交付；二期需求清晰沉淀，随时可启动。
- **结论**：范围控制是「按时闭环」的关键，明确的 Non-Goals 比模糊的「以后再说」更有价值。

### 4. 关键决策即时回填工件
- 用户拍板后（如借用规则三元映射、缺口方向语义、二期登记），立即回填 proposal/design/tasks，不是口头记着。
- **收益**：决策可追溯、可检索，压缩/跨会话不丢。
- **结论**：决策落盘要「即时」，不能攒着。

### 5. 踩坑即时记录（每日志都有「踩坑记录」小节）
- 每个变更的技术坑（Starlette 参数、WPS 样式 bug、namespace 差异、row_idx 偏移等）都当场记进日志。
- **收益**：同类坑下次直接查，不再重新踩。
- **结论**：建立「踩坑清单」是好习惯。

### 6. 面向「可上 GitHub 的能力证明」的高标准
- 项目定位明确为「制造业 Agent 典型案例」，代码注释/README/架构图按展示级标准要求。
- **收益**：倒逼技术选型主流化、文档规范化，避免糊弄式交付。
- **结论**：高标准定位本身是一种质量驱动力。

## 三、有问题的方面（教训，避免走回头路）

### 教训 1（最重）：需求澄清没问到位，导致重大返工
**现象**：需求说明书有「多用户登录」「企业知识库」两条，我在需求分析阶段把它们当「本期简化项/次要细节」做了假设（单管理员、排除知识库），结果它们其实是整套设计的**基石**——用户要的是「多角色底座 + 云端大模型 + RAG」的完整 Agent 案例。

**代价**：tech-architecture 阶段被迫推翻重写（「保持单管理员」→「多角色底座 + 本期单账号过渡」），整个架构定位返工。

**根因**：把「会实质影响 scope 的根本歧义」误判为「次要细节」。
**改进**：需求澄清的分级要更严格——凡是涉及「多用户/多角色」「知识库/数据源」「自然语言/Agent 能力」这类**架构基石级**的词，一律列为必问项，不允许用假设带过。

### 教训 2：技术选型被「隐含」，未单独提审
**现象**：技术选型（前端 Vue3、接口 REST、数据库等）在 system-foundation 里被默认带过，用户事后质疑「架构/选型/契约/数据库什么时候定」，才补了 tech-architecture 变更。

**根因**：把「架构决策」混进了「功能实现」里，没有单独暴露给用户拍板。
**改进**：技术选型属于「需要用户拍板的决策」，应作为独立变更或独立决策点明确提出，不与功能实现捆绑。

### 教训 3：业务语义理解出错，靠用户逐条纠正（J/K 列算法）
**现象**：J/K 列成品计划算法我实现错（把 E 列「未完成数量」当「未完成量」直接用、还跳过区段），用户逐条捋才纠正为 `J/K = max(0, ΣE − ΣF)`。

**根因**：对 Excel 表格的「列语义」和「区段结构」理解不充分就动手写代码。
**改进**：对**手工 Excel 台账/报表**这类「语义藏在列名和布局里」的输入，动手前应先跟用户确认每列的业务含义和区段划分，而不是靠猜测。

### 教训 4：借用行判定差点用错判据
**现象**：差点用「B列规格≠块规格」判定借用行，会误伤内管钳 S73 的跨规格正常行；正确判据是 L 列「见XX」文本。

**根因**：想用一个「看起来能解释现象」的简单规则，没验证它在边界情况（跨规格正常行）下是否会误伤。
**改进**：规则设计要「正向找真判据」，并用反例（会被误伤的样本）做回归，而不是「能用就行」。

### 教训 5：需求原文与范围决策不一致时，未及时同步
**现象**：需求说明书原文有「多用户」「知识库」，范围决策改成了「单管理员」「排除知识库」，但**需求原文一直没改**，直到用户追问才发现偏差。

**根因**：把范围决策当成「内部记录」，没意识到需求原文才是权威基线，必须同步更新。
**改进**：任何范围决策与需求原文冲突时，要么改原文、要么在原文处显式标注「范围差异」，不能两处各说各话。

### 教训 6：把「代码写完、数据验证通过」误当成「完成」，产出半拉子工程（2026-11-01 复盘新增）
**现象**：生产管理排产链路只产出本地 Excel 结果文件、`modules/production/router.py` 仍是占位空壳（`return "待落地"`），却被当成「完成」归档；库存管理前端页写完、接口联调通过，但未经业务方点开确认。

**根因**：① 把「完成」的定义悄悄缩成了「脚本能跑、Excel 出结果」，而不是「用户能在系统里用起来」；② 把「接前端/进系统」错误地和「代码复刻公式」捆绑、一起推迟成二期；③ 验收标准只写了技术行为（联调通过、数据正确），漏掉了「业务方实际使用并确认」这一环（OpenSpec 模板本身不强制此环）。

**改进**：功能变更的验收标准里必须有一条「业务方实际点开/使用并确认」；「接前端/进系统」默认属一期范围，不得擅自划入后续或与其它事项捆绑推迟——「接前端」与「复刻公式」是可拆开的两件事。

## 四、可复用的方法论（沉淀为清单）

### 需求分析阶段
- [ ] 架构基石级需求（多角色/知识库/自然语言/数据源）**必问必确认**，不允许假设带过
- [ ] 需求原文是唯一权威基线，范围决策冲突时同步原文或显式标注
- [ ] 技术选型单独提审，不与功能实现捆绑

### 开发阶段
- [ ] 真实数据早接入，每步实跑 + 对照真实文件核对（数据驱动的验收标准）
- [ ] 手工 Excel 台账的列语义、区段结构，动手前先跟用户确认
- [ ] 规则设计正向找真判据，用反例做回归（防误伤）
- [ ] 「完成」包含「用户能在系统里用起来」——验收须有「业务方点开/使用并确认」一环，「接前端」默认属一期、不与其它事项捆绑推迟

### 决策与记录
- [ ] 用户拍板 → 即时回填工件（proposal/design/tasks）
- [ ] 踩坑即时记录，建立「踩坑清单」
- [ ] 明确一期/二期分界，Non-Goals 写清楚

## 四点五、方法论约束与 OpenSpec skill 的分层关系（防冲突）

> 复盘提炼的「开发协作方法论约束」与 OpenSpec 的 6 个 skill（propose/apply/archive/update/sync/explore）并存，需明确两者关系，避免未来会话因「两套规则打架」而无所适从。

**核心结论：两者是「分层」关系，不冲突。**

| 规则层 | 管什么 | 来源 |
|---|---|---|
| OpenSpec skill | **流程边界**（何时能做什么：propose 只规划不写代码、archive 前查工件、explore 只思考不实现、规划前查 root） | OpenSpec 官方 |
| 复盘方法论约束 | **内容方法**（怎么做才不出错：选型是否提审、Excel 语义是否确认、规则是否反例回归、数据是否实跑） | 本项目复盘 |

两者一个管「何时停」，一个管「如何对」，互不越界。

**唯一重叠点在「需求澄清」**：OpenSpec propose 指令已有「material ambiguity 必问、minor detail 才假设」的规则；复盘铁律①「架构基石级关键词必问」是这条抽象规则的**判定标准细化**（把「material」具体化为「多角色/知识库/RAG/自然语言/云端大模型」等关键词），**不是平行新规则**。执行时以上列关键词「一律必问」为准，避免因「material」门槛抽象而重犯「把多用户当次要细节」的误判。

---

## 五、一句话总结

**流程（OpenSpec 规范驱动）本身是好的、要坚决保持；真正反复出问题的是「需求澄清不够彻底」和「业务语义理解不够深就动手」这两件事——前者导致架构级返工，后者导致算法级返工。以后的新项目，把「问清楚」和「跑真实数据验证」这两件事做在前面，就能大幅减少回头路。**
